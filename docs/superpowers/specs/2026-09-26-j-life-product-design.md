# J의 삶 제품 설계서

> 작성일: 2026-09-26  
> 상태: 구현 전 검토본  
> 대상: Flutter 기반 Android 우선 Local-first MVP

## 1. 제품 목표

`J의 삶`은 월급일, 결제일, 구독 갱신, 차량 정비, 집 관리, 식료품 교체처럼 반복되거나 기한이 있는 생활 항목을 한곳에서 관리하는 앱이다.

사용자는 자신의 생활 방식에 맞춰 메뉴, 카테고리, 템플릿과 대시보드 카드를 구성할 수 있다. 앱은 등록된 일정과 완료 기록을 바탕으로 다음 예정일과 생활·금전 통계를 계산한다.

초기 제품은 서버, 회원가입, 금융 API, 다른 앱 데이터 접근 없이 기기 안에서 완결한다. 반복 사용과 수익이 확인된 범위에만 개발 비용을 재투자한다.

## 2. 성공 기준

MVP는 다음 흐름이 빠르고 안정적으로 반복되는지를 검증한다.

```text
프리셋 선택
→ 생활 항목 등록
→ 예정일과 로컬 알림 확인
→ 완료 처리
→ 다음 일정 자동 생성
→ 대시보드와 통계 확인
```

핵심 제품 지표는 첫 항목 등록률, 3개 이상 등록률, 알림 활성화율, 완료 경험률, 다음 일정 생성 성공률과 30일 유지율이다. 수익화 이후에는 광고 수익, PRO 전환율, 환불률과 유지보수 비용 대비 순이익을 함께 본다.

## 3. 설계 원칙

1. 핵심 기능은 누구나 설명 없이 사용할 수 있어야 한다.
2. 제목과 기준 날짜만으로 항목을 만들 수 있어야 한다.
3. 전문 분야별 앱을 여러 개 만들지 않고 하나의 공통 데이터 구조를 사용한다.
4. 분야별 차이는 템플릿, 선택 필드와 대시보드 카드로 표현한다.
5. 광고는 핵심 작업을 방해하지 않으며 결제 사용자는 광고 영역 자체가 사라진다.
6. 외부 연동보다 로컬 처리와 파일 백업을 우선한다.
7. 실제 사용 및 수익 데이터가 확인된 기능만 확장한다.

## 4. 제품 범위

### 4.1 MVP에 포함

- 생활 항목 등록, 수정, 삭제 및 검색
- 반복 없음, 주·월·년 및 N일·N개월·N년 반복
- 로컬 알림
- 완료 기록과 다음 예정일 자동 계산
- 기본 및 사용자 정의 카테고리
- 분야별 시작 프리셋
- 메뉴 및 대시보드 카드 표시·숨김·순서 변경
- 선택형 금액, 수입·지출 구분
- 등록 항목과 완료 기록 기반 로컬 통계
- 무료/PRO 기능 권한을 분리할 수 있는 내부 구조
- 광고가 들어갈 수 있는 제한된 레이아웃 영역

### 4.2 MVP에서 제외

- 회원가입, 백엔드, 클라우드 동기화
- 은행·카드·금융 API 연동
- 기기 알림 읽기
- 다른 앱의 내부 데이터 접근
- 가계부 수준의 개별 소비 기록과 자산 관리
- OCR, AI, 가족 및 그룹 공유
- 실제 광고 SDK 및 실제 인앱결제 연동
- 구독형 요금제

실제 광고와 결제 SDK는 반복 사용 가능성이 확인된 뒤 출시 준비 단계에서 붙인다. MVP에는 화면 배치와 권한 경계만 포함한다.

## 5. 정보 구조와 화면

### 5.1 첫 실행

사용자는 다음 프리셋 중 하나를 고른다.

- 기본 생활
- 돈·구독 중심
- 차량 중심
- 집 관리 중심

프리셋은 초기 카테고리, 템플릿, 메뉴 순서와 대시보드 구성을 제공한다. 선택 후 모든 설정을 바꿀 수 있으며 프리셋은 데이터를 제한하지 않는다.

### 5.2 홈 대시보드

홈에는 사용자가 선택한 카드만 표시한다. 편집 모드에서 카드를 추가·숨김 처리하고 순서를 바꿀 수 있다.

제공 카드:

- 오늘 할 일
- 곧 해야 할 일
- 이번 달 받을 돈
- 이번 달 나갈 돈
- 이번 달 예상 차액
- 카테고리별 금액 비중
- 월별 수입·지출 비교
- 완료 추이
- 최근 완료 기록

기본 홈은 일정 카드 중심으로 시작한다. 돈 관련 카드와 그래프는 금액 기능을 사용하는 사람만 켤 수 있다.

### 5.3 주요 화면

1. 홈 대시보드
2. 전체 및 카테고리별 항목 목록
3. 항목 등록·수정
4. 항목 상세와 완료 처리
5. 완료 기록
6. 통계
7. 카테고리·템플릿·메뉴·대시보드 관리
8. 설정 및 구매 상태

### 5.4 항목 입력

필수 입력은 제목과 기준 날짜뿐이다. 반복, 알림, 카테고리, 메모, 금액과 수입·지출 구분은 선택값이다.

금액을 입력하지 않은 항목은 돈 관련 통계에서 제외한다. 금액을 입력하면 해당 항목은 예정 금액과 완료 금액 계산에 참여한다.

## 6. 핵심 동작

### 6.1 완료와 반복

사용자가 항목을 완료하면 완료 시각과 당시 금액을 기록한다. 반복 항목은 실제 완료일을 기준으로 다음 예정일을 계산하고 로컬 알림을 다시 예약한다.

월 단위 반복에서 대상 월에 같은 날짜가 없으면 그 달의 마지막 날을 사용한다. 윤년, 말일, 시간대 변경과 일광 절약 시간 변경을 테스트 대상으로 둔다.

### 6.2 금액과 통계

통계는 등록된 생활 항목과 완료 기록만 사용한다.

- 예정 수입·지출: 해당 월에 예정된 항목의 금액 합계
- 확정 수입·지출: 해당 월에 완료된 기록의 금액 합계
- 예상 차액: 예정 수입에서 예정 지출을 뺀 값
- 카테고리 비중: 선택 기간의 지출을 카테고리별로 집계
- 월별 비교: 예정값과 확정값을 구분해 표시

예정값과 확정값은 색상과 레이블로 구분해 실제 잔액처럼 오해하지 않도록 한다. 이 앱은 계좌 잔액이나 모든 소비를 나타내지 않는다는 안내를 통계 화면에 표시한다.

## 7. 데이터 모델

### 7.1 LifeItem

```text
id
title
categoryId
baseDate
repeatType
repeatValue
reminderDaysBefore
lastCompletedAt
nextDueAt
memo
amount (optional)
moneyFlow (none | income | expense)
currency
createdAt
updatedAt
```

### 7.2 LifeHistory

```text
id
lifeItemId
completedAt
amountSnapshot (optional)
moneyFlowSnapshot
memo
```

완료 당시 값을 스냅샷으로 보관해 이후 항목 금액을 바꿔도 과거 통계가 달라지지 않게 한다.

### 7.3 Category

```text
id
name
iconKey
colorKey
sortOrder
isVisible
isBuiltIn
```

### 7.4 DashboardCardConfig

```text
cardType
sortOrder
isVisible
settings
```

`settings`에는 기간, 카테고리 필터와 예정·확정 표시 방식을 저장한다. 지원하지 않는 임의 위젯 코드를 저장하지 않는다.

### 7.5 UserPreferences

```text
selectedPreset
menuOrder
themeMode
defaultCurrency
onboardingCompleted
```

### 7.6 PurchaseEntitlement

```text
tier (free | pro)
productId
purchasedAt
lastVerifiedAt
```

초기에는 개발용 상태만 사용한다. 실제 스토어 결제를 연결할 때 스토어 영수증을 기준으로 검증하도록 교체할 수 있는 경계를 둔다.

## 8. 기술 구조

Flutter 코드베이스 안에서 다음 책임을 분리한다.

```text
presentation
├─ screens
├─ reusable widgets
└─ dashboard cards

application
├─ item use cases
├─ completion and recurrence
├─ statistics
├─ customization
└─ entitlement and ad policy

domain
├─ entities
├─ recurrence rules
├─ statistics rules
└─ repository interfaces

infrastructure
├─ local database
├─ local notifications
├─ preferences
└─ future store/ad adapters
```

UI, 데이터베이스, 알림과 결제 구현이 직접 얽히지 않도록 인터페이스로 분리한다. 분야별 확장은 새 데이터베이스나 독립 앱이 아니라 템플릿, 선택 필드, 통계 카드 또는 제한된 도메인 확장으로 추가한다.

## 9. 광고 및 수익 정책

### 9.1 무료 사용자

- 홈 하단의 고정 네이티브 광고 영역 또는 긴 목록 사이의 제한된 광고 영역만 허용
- 등록, 수정, 상세, 완료 확인과 온보딩에는 광고 미노출
- 전면 광고, 강제 대기, 자동 재생, 소리 재생과 완료 직후 광고 금지
- 광고 로딩 실패 시 빈 여백을 남기지 않음
- 광고와 앱 콘텐츠를 명확히 구분

### 9.2 PRO 일회성 구매

- 광고 및 광고용 여백 완전 제거
- 모든 통계 카드
- 커스텀 카테고리 및 대시보드 확장
- 다중 알림
- 장기 기록과 비교 통계
- JSON/CSV 백업·복원
- 추가 테마 및 향후 편의 기능

핵심 등록·알림·완료 흐름은 무료 사용자도 사용할 수 있어야 한다. 유료 가치는 방해 제거, 개인화, 장기 관리와 편의성에서 만든다.

### 9.3 수익 검증

가격은 구현 단계에서 고정하지 않는다. 출시 전 당시 시장, 스토어 수수료, 세금과 목표 순이익을 기준으로 정한다. 광고 SDK와 결제 SDK는 제품 유지 가능성이 확인된 뒤 연결한다.

```text
무료 MVP 검증
→ 절제된 광고 도입
→ PRO 일회성 구매 도입
→ 순이익 확인
→ 수익 범위 안에서 기능 확장
```

## 10. 확장 전략

사용량과 수익이 확인된 영역만 다음 순서로 확장한다.

| 신호 | 후보 확장 |
|---|---|
| 차량 항목 사용 증가 | 주행거리, 정비 비용, 교체 이력 |
| 구독·돈 항목 사용 증가 | 고정비 비교, 예산, 갱신 최적화 |
| 집 관리 사용 증가 | 설비, 소모품, 관리 이력 |
| 식료품 사용 증가 | 유통기한, 재구매 주기 |
| 백업 요구 증가 | JSON/CSV 내보내기·가져오기 |
| 다기기 요구 증가 | 계정과 동기화의 비용·보안 재검토 |

확장 여부는 요청 수뿐 아니라 예상 개발비, 정책 대응비, 고객 지원비와 순이익을 함께 비교해 결정한다.

## 11. 오류와 예외 처리

- 필수값과 금액 형식을 저장 전에 검증한다.
- 과거 기준 날짜와 기한이 지난 항목도 허용하되 상태를 명확히 표시한다.
- 로컬 알림 권한이 없으면 설정 이동 안내를 제공하고 앱 기능은 계속 사용할 수 있게 한다.
- 알림 예약 실패는 항목 저장 실패로 처리하지 않고 재시도 가능한 상태로 표시한다.
- 삭제 전 영향을 안내하고 최근 삭제는 되돌릴 수 있게 한다.
- 로컬 DB 마이그레이션 실패 시 기존 데이터를 덮어쓰지 않는다.
- 광고·결제 모듈 오류가 핵심 생활 관리 기능을 막지 않게 한다.

## 12. 접근성과 UI 기준

- 한 화면의 주요 행동은 하나로 제한한다.
- 색상만으로 상태를 구분하지 않고 아이콘·텍스트를 함께 사용한다.
- 시스템 글자 크기 확대와 작은 화면에서 핵심 버튼이 잘리지 않아야 한다.
- 그래프에는 수치, 범례와 텍스트 요약을 제공한다.
- 빈 화면에는 관련 템플릿과 첫 항목 추가 버튼을 제안한다.
- 드래그 정렬 외에도 접근 가능한 순서 변경 방법을 제공한다.

## 13. 테스트 전략

### 단위 테스트

- 일·월·년 및 N 단위 반복 계산
- 월말, 윤년과 시간대 경계
- 예정·확정 수입 및 지출 집계
- 과거 금액 스냅샷 유지
- 무료/PRO 기능 및 광고 정책

### 위젯 테스트

- 빈 상태, 오류 상태와 데이터 상태
- 카드 표시·숨김·정렬
- 프리셋 적용 후 사용자 설정 유지
- 큰 글씨와 작은 화면의 핵심 흐름

### 통합 테스트

- 등록 → 알림 예약 → 완료 → 다음 일정 생성
- 앱 재시작 후 데이터·설정 보존
- 항목 수정 후 과거 통계 불변
- 광고 및 결제 모듈 장애 시 핵심 기능 유지

### Android 실기기 검증

- 알림 권한 허용·거부
- 절전 모드와 앱 재시작
- 날짜·시간대 변경
- 장기간 사용할 때 목록과 통계 성능

## 14. 구현 우선순위

1. Flutter 프로젝트와 로컬 데이터 계층
2. 반복 계산, 항목 CRUD와 완료 기록
3. 로컬 알림
4. 프리셋, 카테고리와 템플릿
5. 커스텀 홈 대시보드
6. 금액 필드와 로컬 통계
7. 무료/PRO 권한 및 광고 자리 정책
8. 접근성, 오류 처리와 실기기 검증

3주 MVP 제한을 넘길 위험이 있으면 실제 광고·결제 연동, 고급 그래프, 다중 알림과 파일 백업을 먼저 뒤로 미룬다. 등록·알림·완료·다음 일정 생성의 신뢰성을 희생하지 않는다.
